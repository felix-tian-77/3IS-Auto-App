## 评审方法

按 office-hours 框架的三个核心机制对 PRD 做"压力测试"：
1. **前提挑战** — PRD 中未声明但被默认的假设是否成立

3. **结构完备性** — 企业级 PRD 标准章节是否齐全

## 核心前提挑战（Premise Challenge）

### P1. 矛盾：智能识别 vs 用户指定

**现状。** README §二.1 写"系统自动判别新保/续保类型"；术语表定义 Transaction"由用户提交时指定"；FR-SVR-003 验收标准写"用户提交时指定事务类型后，系统正确分配对应 Flow"。三处表述两两矛盾。

**风险。** 如果"智能识别"是产品叙事，OCR 能力又列在 Out of Scope（§1.4）和外部依赖（AS-003），等于把识别结果当作可信输入但责任不在自己。一旦客户问"你们怎么识别新保续保"，没有任何一段文档能给出答案。

**结论。** 必须二选一：
- **路线甲**（推荐）：放弃"智能识别"叙事，PRD 明确"业务类型由用户在 Web/API 提交时显式指定，错误指定由用户承担"，术语表相应修改。
- **路线乙：真正做识别，OCR 移入 In Scope，§11 风险表中加 OCR 准确率风险。

### P2. 矛盾：Worker 拉文件 vs Device 拉文件

**现状。** README §四的优化说明"将'下载文件'逻辑从客户端剥离至手机端"是正确方向，但 PRD 同时保留：
- FR-CLI-004（Worker 数据拉取，§4.2）
- FR-MOB-002（Device 文件同步，§4.3）

两套并行，调度路径不明（Worker 拉完后转发给 Device？还是 Device 直连？），文件落点也不明（Worker 沙箱？Device 沙箱？）。

**风险。** 实施团队会做出"Worker 拉 + Socket 推给 Device"或"Device 拉 + Worker 透传"两种实现，行为差异在断点续传、错误重试、加密沙箱上全部体现。**这是典型的"PRD 留白 = 实施分歧"。**

**结论。** 标记 FR-CLI-004 为 DEPRECATED，统一走 FR-MOB-002（Device 直连 OSS 签名 URL），Worker 只做指令中转。

### P3. 误判：CONFIRM Step 破坏价值主张

**现状。** 价值主张 §1.3 写"3-5 分钟自动化"。但 §3.4 状态机允许 `WAITING_CONFIRM` 暂停 30 分钟（默认 confirm_timeout_ms = 1800000ms）。客户真实等待时长 = 自动化 3-5 分钟 + 确认 0-30 分钟，平均场景比纯人工还慢。

**风险。** 销售团队抱怨"用机器人反而更慢"，影响规模化推广。

**结论。** 见下文"方案 B / 方案 C"，CONFIRM Step 必须重构或废弃。

### P4. 误判：MVP 数据库轮询的可扩展性

**现状。** §7.7 说 MVP 用 `SELECT FOR UPDATE SKIP LOCKED` 做任务队列；NAC-001 要求 50 笔/分 × 30 分钟持续；§7.7 又写"调度中心无状态化横向扩展"。

**风险。** "无状态调度中心 + DB 行锁轮询"是矛盾的：DB 行锁天然引入协调开销，调度中心多副本时会出现：
- 同一笔事务被两个副本同时领取（除非 SKIP LOCKED 严格）
- 调度延迟抖动（轮询间隔 × 副本数）
- DB CPU 压力（每个副本都轮询同一张表）

50 笔/分 = 0.83 笔/秒，DB 撑得住，但延迟 P95 很可能超 2s（NFR §8.1）。

**结论。** MVP 阶段必须明确二选一：
- 单活调度中心（副本只做高可用，不同时抢活）
- 直接引入 Redis Stream（即使成本增加 30%，也比 P0 事故划算）

### P5. 缺口：数据合规与隐私

**现状。** §8.3 提到加密存储，但缺失：
- 加密密钥管理（KMS？谁的 IAM 权限？）
- 跨境传输合规（OSS 地域选择）
- PIPL 第二十四条"敏感个人信息"处理规则
- 《保险法》第二十一条"投保数据至少保存 10 年"
- 数据主体权利 API（删除、导出）

**风险。** 客户合规审核直接打回，**这是合同签订前的硬卡点**。

**结论。** 新增 §2.5 "数据合规与隐私"，含完整合规对照表。

### P6. 缺口：可观测性是空话

**现状。** §8.4 写"统一采集至日志平台"但没指定：指标名规范、TraceID 透传规则、采样率、关键 SLO、告警通道。

**风险。** 上线后排查问题靠猜，团队陷入"重启能解决一切"的反模式。

**结论。** §8.4 改为具体技术选型（Prometheus + Loki + Tempo，OpenTelemetry SDK，RED/USE 指标体系），并定义初始告警规则集。

### P7. 缺口：测试策略

**现状。** 完全没有测试章节。§10 验收标准 26 条全靠"现场跑一次"判定。

**风险。** RPA 系统最致命的故障是"UI 变更 → 脚本失效"，每次保险 APP 更新都会触发。需要：
- 脚本单元测试（mock 设备接口）
- 录屏回归（每次发布前回放 100 条历史事务）
- 端到端契约测试（API 兼容性）

**结论。** 新增 §10.3 "测试策略"，明确四层测试矩阵。

## 架构级替代方案

### 方案 A：瘦服务端 + 胖 Worker（推荐）

**目标。** 解决 P2 矛盾 + 提升单机 Worker 容量。

**核心改动。**
- 标记 FR-CLI-004 为 DEPRECATED
- 新增 API：`POST /api/v1/transactions/{id}/oss-urls`（生成 Device 可直接访问的签名 URL 列表，TTL 5min）
- Worker 收到任务后只下发 `{transaction_id, file_urls, md5}` 给 Device
- Device 自己用 FR-MOB-002 流程下载、校验、入库
- Worker 不再持有影像字节流，只持有元数据

**优势。**
- Worker 不再吃存储 IO 与带宽，扩容瓶颈消失
- OSS 签名 URL 过期机制天然防泄漏（无需额外加密沙箱设计）
- 失败定位清晰：下载失败 = Device 问题，不影响 Worker 调度

**代价。**
- 需要保证 OSS 在公网可访问（不能放在内网）
- FR-CLI-004 现有实现需要从代码移除（影响约 200-300 行）

**工作量。** 中等（PRD 修改 + 1 个新 API + 1 个客户端移除 + 1 个设备端扩展）。

### 方案 B：去掉 CONFIRM Step，改预填 + 单次确认

**目标。** 解决 P3 矛盾，恢复"3-5 分钟"价值主张。

**核心改动。**
- 新增"服务端预填"组件（依赖 AS-003 OCR 服务）
- Flow 中把 CONFIRM Step 改为"截图回传" Step：机器人填完表单后截一张图上传，状态变为 `WAITING_CONFIRM`，**只等一次确认**
- 用户在 Web 看到预填结果，点"确认提交"才进入"提交 Step"
- 取消"超时自动通过"机制，超时 = 失败进 DLQ

**优势。**
- 单事务真实时长：30s 自动化 + 5-10s 用户确认 ≈ 1 分钟内完成
- 用户有掌控感（"我看到了机器人填的，再确认"），不焦虑
- 取消"30 分钟超时"这种反人性的兜底

**代价。**
- 必须先有 OCR 服务（引入新外部依赖，§11.2 补登记）
- 仍然依赖用户操作，**不是真"无人值守"**

**工作量。** 中等（OCR 集成 + 流程重写 + 状态机调整）。

### 方案 C：去掉 CONFIRM Step，全自动化 + 异步审计

**目标。** 解决 P3 矛盾 + 极致吞吐（>5000 笔/日）。

**核心改动。**
- 整个 Flow 不再有任何用户交互
- 每步执行后截图 + 关键字段值上传到 Backend
- 失败的事务进 DLQ，运维事后审计 + 决定是否重试
- 销售只在前端看"已成功"或"异常待人工"

**优势。**
- 真正的"无人值守"，单事务时长 = 纯自动化时间（<3 分钟）
- 吞吐瓶颈只剩设备数量，可线性扩展
- 没有"用户忘记确认"的悬而未决

**代价。**
- 对 AS-001（保险 APP UI 稳定性）要求极高
- 失败率必须 < 0.5% 才不烧穿运维人力
- 客户接受度低：销售不放心机器人提交

**工作量。** 较大（移除 CONFIRM 状态机 + DLQ 工作流 + 审计后台）。

### 方案 D：MVP 直接引入 Redis Stream（备选）

**目标。** 解决 P4 矛盾，避免数据库轮询的隐性坑。

**核心改动。**
- §7.7 演进路径里把 Redis 从"可选中期"前移到"MVP 必需"
- 用 Redis Stream + Consumer Group 做任务队列
- 调度中心作为消费者，DB 只做结果持久化

**优势。**
- 调度延迟从 P95 2s 降到 P95 < 200ms
- 多副本调度中心天然支持（消费者组自动分配）
- 削峰能力强（突发 10×流量不爆）

**代价。**
- 增加 1 个云组件 + 监控对象
- 客户端 SDK 简单（redis-py 已成熟）

**工作量。** 小（仅调度中心改造，业务代码不动）。

### 方案选型建议

| 场景 | 推荐组合 | 理由 |
|------|----------|------|
| 试点 1-2 站点、日 < 500 笔 | A + D | 解 P2 + P4，工程量小，立竿见影 |
| 商业推广、日 500-3000 笔 | A + B + D | 恢复价值主张，吞吐可扩展 |
| 大客户、> 5000 笔/日 | A + C + D | 极致自动化，运维前置 |

## 缺失章节清单

**必须新增（不补无法过企业评审）：**

1. **§1.5 术语约定补充** — "事务"在 DB / 业务 / RPC 三个语境下的不同含义

4. **§7.8 灾备设计** — DB 跨可用区、OSS 跨地域复制、RPO/RTO 数字
5. **§8.7 容量规划模型** — 用户数 / 事务量 / 设备数 / 存储增长 四张曲线
6. **§9.x 成本估算** — MVP 阶段云资源月费上限、扩容阈值
7. **§10.3 测试策略** — 单元 / 契约 / 端到端 / 录屏回归 各自覆盖
8. **§12 发布与变更管理** — 灰度策略、版本回滚 SLA、客户端强制升级
9. **§13 运营手册索引** — 日常运维、扩缩容、故障响应跳转
10. **§14 开放问题** — 当前未决项（OCR 接入？多保险公司扩展？）

## 开放问题

需要在评审会上讨论：
- **Q1.** 销售团队能接受"机器人提交后无法撤回"吗？（影响方案 B vs C 选型）
- **Q2.** 当前保险 APP 的 UI 稳定性？最近半年更新频次？（影响 AS-001 假设是否成立）
- **Q3.** OCR 服务是采购还是自建？SLA 承诺？（影响方案 B 是否可行）
- **Q4.** 客户对数据存储地域有要求吗？（影响 OSS 选型与合规）
- **Q5.** 是否需要支持"中途人工接管"（机器人失败时人继续填）？（影响 FR-MOB 设计）

## What I noticed about how you think

- 你把 PRD 写成"功能列表 + 状态机 + ER 图"的硬核工程风格，不是叙事型产品 PRD — 团队技术力强
- 你把 AS-001 ~ AS-006 假设前提单独列出，这是少见的好习惯（多数 PRD 假设混在叙述里）— 体现风险意识
- §7.7 演进路径的分阶段写法说明你考虑过成本节奏，**但 P4 暴露"分阶段"和"无状态调度"的内在矛盾尚未识别** — 这是工程师视角盲区，建议下次评审时把"演进路径"先和"核心架构"对齐
- §10 验收标准有 26 条且全部可测 — 工程纪律好，但完全没提"怎么测"，说明你相信"自然能跑" — 这种信心在 RPA 场景会吃亏
- 文档唯一一处英文 "Airtest" 没有注释，术语表也没有 — 国际化和团队扩展时会有翻译成本，建议补
