## 核心前提挑战（Premise Challenge）

### P1.【高】V1.2 残留的 OSS 引用未清干净

**现状。** V1.3 决定废弃 OSS-first 设计，但 PRD 中仍有 86 处 "OSS" 引用。逐一排查后，发现以下**实际冲突**：

- **§3.6 BCP 表第 1 行**：`云端 Backend 全部故障 | 销售可继续提交（写入 OSS 直传通道）`——V1.3 已废 OSS 直传通道，此条应改为"写入 Backend 暂存"
- **§3.6 BCP 表**：`OSS 不可用 | 影像上传和下载失败`——V1.3 默认 LocalStorageBackend，此条描述的是 OssStorageBackend 的 V1.4+ 行为；V1.3 应改为"存储后端不可用（通用）"
- **§4.1 FR-SVR-001 验收**：原文 `事务+文件不一致返回 422`——但 V1.3 多文件 multipart 提交，5/6 文件成功 + 1 失败时如何处理未定义
- **§7.4 网络要求表**：`Device → OSS | HTTPS | 443 | 出站 | Device 直接从 OSS 下载文件（V1.2 仍由 Device 直连，不经 Worker）`——V1.3 已不再走 OSS
- **§11.2 外部依赖**：`OSS 地域（V1.1 新增）`行整行保留——V1.3 应当 DEPRECATED 或重写

**风险。** 实施团队读到 PRD 冲突处会做"自由心证"。如 1.5 人周实现，谁负责把"OSS 直传通道"实现出来？

**结论。** V1.3 进入 Review 之前必须做"OSS 引用清理"扫描，输出 diff 单独成节。

### P2.【高】URL 签名机制完全未定义

**现状。** V1.3 新增 `POST /api/v1/transactions/{id}/download-urls` 接口，§6.2.1 示例中 URL 形如：
```
https://api.example.com/api/v1/downloads/DURL-20260605-00001?token={sig}&expires=1749050700
```
`{sig}` 是签名，但 **PRD 全文没有说明 `sig` 如何生成**：
- JWT？HMAC-SHA256？随机 token 查表？
- 签名密钥存在哪？KMS？环境变量？HSM？
- Token 包含哪些 claim？（device_id？txn_id？ip？）
- 是否有 replay 防护？（一次性 token？消费即失效？）
- URL 中同时出现 `?token=` 和 `Authorization: Bearer {device_token}`，**两者关系**是 AND 还是 OR？

**风险。** 这是 **安全关键路径**。如果实现者选了"随机 token 查表"方案，Backend 重启时内存丢失导致所有 URL 失效；如果选了"长 token 不查表"方案，泄漏 = 永久访问；如果选了 JWT 而密钥泄露，攻击者可签发任意 URL。

**结论。** 必须新增 §9.1 章节"URL 签名机制"，至少定义：
- 签名算法（推荐 HMAC-SHA256 + 包含 device_id + expires 的 payload）
- 密钥管理（推荐 KMS 托管的 secret_key）
- 验证路径（GET /api/v1/downloads/{url_id} 时如何校验）
- 一次性消费（消费后 url_id 标记 consumed_at，重复消费返回 410）

### P3.【高】V1.2 → V1.3 迁移策略模糊

**现状。** §12 说"渐进式双轨 3 个月"，§15 关联文档提到"历史 OSS 附件保留可读"。但：

- **3 个月内 V1.2 的 `file_url`（OSS URL）事务如何被 V1.3 Backend 服务？**
  - 方案 A：V1.3 Backend 保留 OSS 读权限，按需代理
  - 方案 B：3 个月前批量从 OSS 迁到 V1.3 LocalStorage
  - 方案 C：3 个月后强制这些老事务 FAIL
  - **PRD 未指定**
- **V1.3 Backend 是否需要保留 OSS SDK？** 若是 1 个 ECS 进程同时挂 LocalStorage 和 OssStorage 适配器，配置更复杂
- **3 个月到期后老事务的 device 还在跑（device 端只感知 URL）**——如果 V1.3 不再支持 OSS URL 直连，老事务在第 91 天 FAIL

**风险。** 销售侧可能有"3 个月内回看老事务"的需求。如果老事务的附件在 V1.3 不可读，运维就要做数据迁移；这件事 PRD 没有 R&R（谁负责、什么时间窗口、SLA 多长）。

**结论。** §12 迁移策略需要展开为 3 个具体子任务：
- 任务 1：批量迁移 V1.2 OSS 附件到 V1.3 LocalStorage（脚本 + 校验）
- 任务 2：V1.3 Backend 是否保留 OssReadOnly 适配器（V1.3 期间可读 V1.2 数据）
- 任务 3：3 个月到期前对未完成老事务的处理（强制 FAIL？延后清理？）

### P4.【高】灾备策略提了但未设计

**现状。** §11.1 风险表新增"Backend 单点存储"，缓解措施写"Backend 双实例 + 文件同步（如 DRBD / rsync / 共享存储）"。NAC-V13-003 说 RTO ≤ 30min。

但以下均未指定：
- **DRBD 是 active-passive 还是 active-active？**（active-active 写入冲突需要处理）
- **2 个 Backend 实例的文件目录树如何保证一致？**（写本地 + 同步到对端 vs 共享挂载）
- **如果用共享存储（NFS/OSS-as-shared），NFS 本身 SPOF？**
- **RTO ≤ 30min 的具体流程？**（检测 → 切换 → 启动 → 数据一致 → 接管流量）
- **RPO 多少？**（DRBD 同步模式 = 0 RPO；rsync 定时 = 几分钟 RPO）
- **K8s StatefulSet 双实例怎么挂同一份 PV？**（ReadWriteMany PV 还是分别挂载？）

**风险。** "Backend 双实例 + DRBD"是 1 个字的描述。**实施时可能变成 3 套不同的方案**（DRBD、rsync、共享存储），每套 RTO/RPO 不一样，无法达到 NAC-V13-003 的承诺。

**结论。** 必须新增 §7.9 "V1.3 存储灾备设计"章节，明确：
- 灾备模式（推荐 DRBD active-passive，RPO=0，RTO ≤ 5min）
- K8s 部署方式（StatefulSet + ReadWriteOnce PV × 2）
- 故障切换流程（半自动：人工确认 → 切换 → 接管）
- 定期演练（每月 1 次）

### P5.【中】1TB SSD 数字缺论证

**现状。** §7.5 写"1TB SSD × 2 实例"。Q12 说"500 笔/日 × 5MB × 30 天 ≈ 75GB/月"，但没算客户量增长曲线或保险 APP 文件大小分布。

- **附件大小不是均匀 5MB**：身份证 1-3MB，行驶证 1-2MB，合格证 5-10MB，发票 0.5-2MB。均值可能 3-8MB
- **保留期**：V1.3 写"事务完成后 > 7 天清理"，意味着 7 天窗口期所有附件都还在
- **峰值 vs 均值**：早 9-10 点可能日均 30% 集中提交（5x 倍数）

如果日均 500 笔 × 平均 5MB × 7 天保留 = 17.5GB（峰值日 87.5GB）。1TB SSD 够 80 天用量。**问题**：
- **V1.3 业务扩展到 1000 笔/日时，1TB 还能撑多久？**（约 40 天）
- **V1.3 引入"事务级文件保留 7 天"，那 7 天前的旧事务的 ATTACHMENT 实体是否需要保留？** 仅需 metadata（用于审计），文件本身可清理。**这点 PRD 没说**

**结论。** §8.7 容量规划需要补充：
- 附件大小分布假设（基于目标保险 APP 实际样本）
- 7 天保留策略的明确语义（保留 metadata？仅文件？都保留？）
- 业务量增长下的扩容触发条件（从 1TB → 2TB 的具体节点）

### P6.【中】Multipart 提交失败回滚语义未定义

**现状。** §4.1 FR-SVR-001 验收写"事务+文件原子性（任一校验失败回滚）"。但 multipart 提交 5/6 文件成功 + 1 失败时：

- **Backend 何时校验？**（收到所有文件后再校验？还是收一个校验一个？）
- **部分文件已落地（写到 LocalStorage），校验失败如何回滚？**
  - 方案 A：保留文件，事务 FAIL，下次重试时通过 attachment_id 去重（增量上传）
  - 方案 B：删除已落地的文件，事务 FAIL
  - 方案 C：保留文件 + 标记 orphan，定期 GC
- **MD5 校验失败时如何处理？**（重传？报错？）

**风险。** LocalStorageBackend 1TB 容量中可能积累大量 orphan 文件，最终触发"磁盘满 507"。

**结论。** 需要明确 multipart 失败语义，推荐方案 A（保留 + 标记 orphan + GC），并在 §4.1 增加 FR-SVR-023 "存储对象 GC"需求。

### P7.【中】Backend 服务公网暴露下载端点的安全后果

**现状。** §2.5 合规把"OSS 地域约束"泛化为"存储后端地域约束"。AS-013 假设"Backend 服务可对外暴露 `GET /api/v1/downloads/{url_id}` 端点"。

但 V1.1/V1.2 时代 Backend 仅在云上（无需对 Device 公网直连）。V1.3 翻转后：
- **Device 端到 Backend 的下载 URL 需公网可达**——这意味着 Backend 服务必须暴露在公网，或开专线
- **PIPL 合规**：身份证 + 行驶证是敏感个人信息，Backend 端点必须受 SLB + WAF + 限流保护
- **设备鉴权**：Device 通过 USB ADB 在 Worker 后面，Device 自身没有公网 IP——那"Device 直连 Backend 下载"在物理上是怎么连的？

**风险。** 这是 §3.1 主流程"Device 直连 Backend"在物理拓扑上未明确的问题。可能的方案：
- Worker 转发（破坏 V1.2 的"Worker 不中转字节流"）
- Device 走 USB ADB 反向网络（Airtest 支持，但需 Airtest 框架配合）
- 站点开 VPN（运营成本）

**结论。** §3.1 需要明确 Device 物理连接路径，并联动 §7.4 网络要求。

### P8.【低】下载 URL 续签的 Retry 语义

**现状。** FR-MOB-006 + AC-NEW-V13-005：URL 过期前 1min 主动续签；连续 3 次失败该事务置 FAIL。

但：
- **续签是否需要 Device 端调用** `POST /api/v1/downloads/{url_id}/refresh`？还是 Worker 代理？
- **续签后新 URL 是否仍指同一 url_id？**（影响 Device 端缓存）
- **续签时的 device_id 校验**（防止 URL 被劫持续签到不同设备）？

**风险。** 这些不复杂，但实现细节若团队理解不一致会有 bug。

**结论。** §6.2.1 续签接口文档需要补充 request/response 完整示例和以上细节。

---

### P9.【低】多租户隔离未设计

**现状。** §2.5 提到"客户指定地域"，但**单 Backend 实例服务多客户**时：
- 存储命名空间是否带 customer_id？(`/data/attachments/{customer_id}/ATT-xxx/...`)
- 跨客户访问防护（一个客户的 sales 不能读另一个客户的 attachment）
- URL token 是否绑定 customer_id？

**结论。** V1.3 MVP 是否多租户？若是，需在 Attachment 实体增加 `customer_id` 字段；URL token claim 包含 customer_id。

## 架构级替代方案

### 方案 A：V1.3 当前选择（Server-first + LocalStorageBackend）— 评分 7/10

**目标。** MVP 简单、低成本、运维自主。

**核心决策。**
- 客户端 multipart 一并上传
- Backend LocalStorageBackend（默认）
- 抽象 StorageBackend 支持未来切 OSS

**优势。**
- MVP 启动成本低（无 OSS 部署）
- 数据完全自主（合规友好）
- StorageBackend 抽象提供未来弹性

**劣势。**
- **灾备方案 DRBD 未设计**（参见 P4）
- **单 Backend 实例 1TB SSD 容量上限**（参见 P5）
- **URL 签名机制未定义**（参见 P2）

**工作量。** 取决于灾备方案选择（DRBD=1 周，共享存储=2 周，rsync=3 天）

---

### 方案 B：Server-first + MinIO 内置（推荐替代）— 评分 8/10

**目标。** 保留 Server-first 的优势，但解决灾备和容量扩展问题。

**核心改动。**
- 保留 V1.3 的 StorageBackend 抽象
- 默认后端改为 `MinioStorageBackend`（自建 MinIO 集群，3 节点起步）
- MinIO 集群：3 节点 × 4TB HDD = 12TB 可用，分布式 EC 编码，自动修复
- Backend 仍然 multipart 上传，文件落到 MinIO

**优势。**
- **容量可扩展**：3 节点 → 6 节点线性扩容
- **高可用内置**：MinIO 容忍 1 节点故障
- **抽象层复用**：未来切 OSS 时改配置即可
- **PIPL 合规**：所有数据在客户 VPC 内

**劣势。**
- 新增 MinIO 集群运维（3 节点 + 监控）
- 月成本增加 ¥1500-2000（3 × 中等 ECS）
- 网络拓扑复杂（Backend → MinIO 内网）

**工作量。** MinIO 集群部署 3 天 + Backend 改造 2 天 + 集成测试 2 天 = 1 周

---

### 方案 C：Server-first + Backend StatefulSet + 共享块存储（折中）— 评分 6/10

**目标。** 不引入新组件，靠云厂商共享块存储解决灾备。

**核心改动。**
- Backend 改 K8s StatefulSet（不再 Deployment）
- 挂载云厂商共享块存储（如阿里云 ESSD，同步复制多可用区）
- 文件落到共享块存储

**优势。**
- 灾备由云厂商保障（RPO=0）
- 不引入新组件

**劣势。**
- **云厂商绑定**（难换云）
- 共享块存储成本高
- 单 Backend 实例仍受单节点性能限制

**工作量。** K8s StatefulSet 改造 1 周

---

### 方案 D：保持 V1.2 OSS-first + 优化上传体验（倒退）— 评分 5/10

**目标。** V1.3 翻转是错误决定，回到 V1.2 并优化。

**核心改动。**
- 恢复 V1.2 客户端先传 OSS 设计
- 新增预签名 multipart 上传支持（client 用 OSS SDK 直接上传 100MB+ 大文件）
- Backend 仅接收 file_url

**优势。**
- 不需要 Backend 大存储
- 客户端直接走 OSS 带宽，不占 Backend
- 灾备由 OSS 提供

**劣势。**
- **V1.2 的"OSS 桶需公网可访问"合规风险**（V1.3 已解决）
- **V1.2 的客户端复杂度**（先传 OSS，再调 API，2 步）

**工作量。** 倒退，1-2 周可恢复

**适用场景。** 仅当 V1.3 翻转决策本身被推翻时考虑。

---

### 方案选型建议

| 场景 | 推荐 | 理由 |
|------|------|------|
| MVP ≤ 1 站点、日 ≤ 100 笔 | A（V1.3 当前） | 简单够用；DRBD 灾备可以延后 |
| 商业推广、日 500-2000 笔 | **B（MinIO）** | 容量 + 灾备 + 合规三赢 |
| 私有化部署、客户机房 | C（共享块存储） | 不引入新组件 |
| 跨地域部署 | D（回到 OSS） | OSS 跨地域复制成熟 |

**当前 V1.3 选 A，但应在 §14 开放问题中明确"B 是中期推荐方案"，给读者留预期。**

## 缺失章节清单

V1.3 新增存储相关内容，但缺少以下配套章节：

1. **§9.1 StorageBackend 接口契约** — 详细的接口签名、错误码、异常类、重试策略

## What I noticed about how this V1.3 was authored

- **V1.3 翻转决策果断**——从 OSS-first 翻到 Server-first 用了 1 个 brainstorming session，5 个关键决策点全部明确。这一点比 V1.2 的"渐进式" 更成熟。
- **StorageBackend 抽象**做得正确——把"存储"和"签名 URL 生成"都抽象到接口里，未来切后端零业务代码改动。这是 V1.3 最有价值的决策。
- **V1.1/V1.2 的 DEPRECATED 风格延续得好**——30+ 处的 [DEPRECATED, V1.X] 标记让版本演进有迹可循。
- **但 V1.3 缺一个"安全设计"专章**——URL 签名机制是 V1.3 整个存储体系的安全基石，全文没有一段定义。**这是最大的疏忽**。
- **灾备策略"提了但没设计"**——比 V1.1 时更好（至少提到了），但还没到可落地的程度。
- **86 处 OSS 引用**说明 V1.3 是"基于 V1.2 增量修订"而不是"重写"，这种做法效率高但残留难清。
